# RecoverAI — Architectural Decision Records (ADR 001 – 010)

## ADR-001: Modular Monolith vs Distributed Microservices
- **Status**: Accepted
- **Context**: Autonomous recovery requires transactional guarantees across webhook ingestion, event ledgers, and recovery state machines.
- **Decision**: Build RecoverAI as a Turborepo-managed Modular Monolith (NestJS API + BullMQ Worker + Next.js Web) sharing strongly-typed domain packages.
- **Consequences**: Single deployment pipeline, atomic database transactions via PostgreSQL, zero network serialization latency between core modules.

---

## ADR-002: Single Orchestrator vs Multi-Agent Swarm
- **Status**: Accepted
- **Context**: Multi-agent LLM conversations introduce unpredictable state spaces, compounding token costs, and nondeterministic loops.
- **Decision**: Adopt a Single Orchestrator AI architecture bounded by deterministic domain services, strict JSON Zod output schemas, and a hard sub-1500ms fallback timeout.
- **Consequences**: Provable worst-case latencies (< 5ms fallback), deterministic audit trail, and zero conversational hallucinations.

---

## ADR-003: Raw Buffer Webhook Signature Verification
- **Status**: Accepted
- **Context**: Razorpay HMAC SHA-256 signatures depend on exact byte-level UTF-8 payloads. JSON re-serialization breaks signature validation.
- **Decision**: Preserve `req.rawBody` buffer in NestJS API before deserialization and execute timing-safe HMAC equality checks.
- **Consequences**: 100% cryptographic reliability, immunity to JSON key reordering attacks.

---

## ADR-004: Transactional Outbox Pattern for Customer Communications
- **Status**: Accepted
- **Context**: Dual-write problems between database mutations and third-party notification APIs (Email/SMS/WhatsApp) can cause orphaned messages.
- **Decision**: Persist all customer notifications into the `notification_outbox` table within the primary DB transaction before worker dispatch.
- **Consequences**: At-least-once guaranteed delivery, complete idempotency across retries.

---

## ADR-005: Zero Cardholder Data Retention (PCI Scope Minimization)
- **Status**: Accepted
- **Context**: Direct handling of PAN/CVV brings strict PCI DSS Level 1 audit scopes.
- **Decision**: Never accept or persist PAN, CVV, or cardholder credentials. Strictly store Razorpay tokenized reference IDs (`pay_xxx`, `order_xxx`).
- **Consequences**: Massive reduction in regulatory burden and surface area for compromise.

---

## ADR-006: Deterministic Policy Engine & Maker-Checker Dual Authorization
- **Status**: Accepted
- **Context**: Autonomous AI actions involving discounts, refunds, or high-value amounts pose financial exposure.
- **Decision**: Implement a first-class Policy Engine enforcing strict rules DSL. Actions exceeding ₹10,000 or applying discounts > ₹100 mandate human Maker-Checker approval (`reviewed_by_id != requested_by_id`).
- **Consequences**: Elimination of unauthorized automated capital movement.

---

## ADR-007: Sub-25ms Webhook Ingestion SLA
- **Status**: Accepted
- **Context**: Payment gateways require rapid 200 OK acknowledgments to avoid retry storms.
- **Decision**: Webhook endpoint performs only HMAC validation, SHA-256 payload deduplication ledger insertion, and BullMQ enqueuing, immediately responding in < 25ms.
- **Consequences**: Maximum resilience against traffic surges without worker backpressure affecting gateway SLAs.

---

## ADR-008: AES-256-GCM Field Encryption at Rest
- **Status**: Accepted
- **Context**: Merchant API secrets, webhook signing keys, and customer MFA secrets require encryption at rest.
- **Decision**: Encrypt all secrets using AES-256-GCM with unique 12-byte initialization vectors (IVs) and 16-byte authentication tags.
- **Consequences**: Tamper-proof, cryptographically secure storage across all tenant rows.

---

## ADR-009: 30-Minute Automated State Convergence & Reconciliation
- **Status**: Accepted
- **Context**: Webhooks can be lost, delayed, or delivered out of order.
- **Decision**: Run a periodic 30-minute reconciliation job querying Razorpay APIs for unresolved cases, converging local state with the gateway source of truth.
- **Consequences**: Zero stale recovery cases; automatic self-healing.

---

## ADR-010: Opaque 32-Byte Tokens for Customer Recovery Web Portal
- **Status**: Accepted
- **Context**: Customer payment recovery links sent via SMS/Email must not expose internal database IDs or merchant credentials.
- **Decision**: Generate cryptographically random 32-byte opaque tokens, storing only SHA-256 hashes in PostgreSQL.
- **Consequences**: Complete protection against IDOR and enumeration attacks on public recovery links.
